# 追加実験の方針：構造情報の要素別寄与（目的2）とパラメータ決定法

**対象論文**：`IN_KishiMaiko.pdf`（IEICE 技術研究報告／査読なし、2026）
「Authorization Cache for Cross-Graph Random Walk Analysis Considering Access Locality」
**対応実装**：`base/proposed_cache/virtual_server_dualpool.py`（＋ import 元の `virtual_server_sim_reuse_score.py` / `split_remote_server_reuse_score.py` の `PPRBoundedCache`）

> 注：`M_Research/paper_draft_v6.md` は別系列の草稿（`reuse_score`：学習項 L・二段階運用・RTT 評価あり）。本計画は IN 稿＝デュアルプール系列を主対象とする。v6 との差分は §6 に退避。

---

## 0. 結論（方針サマリ）

1. **論文の式と実装は、骨格レベルでは一致している。** `Priority = Base + w·Value`、`Base` = LRU 最終アクセス時刻、`w=0` で厳密 LRU、`Close`/`Deg` の Welford 標準化＋logistic で [1,2)、エッジは `Deg` を使わない、ノード/エッジ別プール — すべて実装どおり。残る不一致は**4点**（§1.3）で、いずれも「論文に書かれていないパラメータ・変換がある」タイプ。
2. **ただし図表間で設定が食い違っている。** 表1・図7 は **γ=1（次数 ON）**、図8 は **γ=0（次数 OFF、`node_deg_exp=0.0`）** で描かれている。本文 §5.2 は「β=γ=1 と固定」と書いているため、**図8 と本文が矛盾**する。しかも γ=0 の方が良い（+7.0 pt vs 表1 の +6.6 pt）。→ **これは追加実験の結論そのもの**なので、対照実験で正面から扱うべき。
3. **対照実験（目的2）の最重要欠落は「プール分離だけの効果」。** 表1 は 提案（分離＋スコア）vs LRU（共有）なので、+6.6/+7.1 pt のうち何 pt が**容量をノード/エッジに分けただけ**で得られたのか分離できていない。`run_dualpool` に `w_node=w_edge=0` を渡せば「分離 LRU」が**1ランで**測れる。最も安く、最も効く追加実験。
4. **パラメータの決め方は「自動決定／設計固定／探索」の3層で既に整理されている**（§5.2）。足すべきは (a) 隠れパラメータ3つ（C_F・容量配分・w_edge/w_node）の開示と感度、(b) 最適 w のグラフ間一致（現在 図8 は VLDB のみ）、(c) 山なりの平坦性の定量化。

## 1. 論文の式 vs 実装

### 1.1 論文（§4.2, §4.3）

```
Priority(e) = Base(e) + w · Value(e)                    ← Priority 最小を退去
Base(e) = 既存キャッシュ方式の優先度（LRU では最終アクセス時刻）, w=0 で既存方式へ厳密に戻る
Value_node(e) = Freq(e)^θ · Close(e)^β · Deg(e)^γ
Value_edge(e) = Freq(e)^θ · Close(e)^β                  ← 次数は再利用性と逆方向なので含めない
Close(e) = 1 + σ((μ_hop − hop(e)) / s_hop)              ← Welford で μ,s を逐次更新
Deg(e)   = 1 + σ((deg(e) − μ_deg) / s_deg)              ← 同上、共通の値域 [1,2)
Freq(e) = 認可結果がキャッシュに保持されている間の使用回数
ノードとエッジを独立したキャッシュで管理（§4.3）。1エントリの占有量が異なる場合は占有量を考慮
```

### 1.2 実装（`virtual_server_dualpool.py` + `PPRBoundedCache`）

```
Priority(e) = last_access(e) + w · Value(e) / size(e)                    _h_value()
Value(e)    = O(e)^θ · prior(e)                                          _score()
O(e)        = 1 + Freq(e) / (Freq(e) + C_F)          C_F = 5             ← ★飽和正規化
prior_node  = (1+σ(z_hop))^{node_hop_exp} · (1+σ(z_deg))^{node_deg_exp}  node_prior()
prior_edge  = (1+σ(z_hop))                                               edge_prior()
node_cache / edge_cache を別インスタンスで保持                            run_dualpool()
既定: cap_node=40, cap_edge=60, w_node=100, w_edge=300, θ=1
size: node エントリ=2, edge エントリ=3（DecisionCacheSizer: start 1 + node 1 / edge 2）
lambda_learn=0, rho=0 → 学習項 L と最近性項 R は無効（＝論文に無いものは使っていない）
```

### 1.3 残る不一致（4点）

| # | 論文 | 実装 | 影響と扱い |
|---|---|---|---|
| **1** | `Freq(e)^θ`、Freq は**生の使用回数**（正規化するのは「Close と Deg の両者」と明記） | `(1 + Freq/(Freq+C_F))^θ`、**C_F=5 の飽和関数で [1,2) に正規化**。C_F は論文に登場しない | ★**唯一の実質的な式の不一致。** Freq=1/10/100 に対し 論文式=1/10/100（桁で支配）、実装式=1.17/1.67/1.95（高々2倍）。**実装の方が論文の設計意図（全特徴量を同一尺度で比較）に忠実**で、記述が実装に追いついていない。さらに §5.4 の観測「θ≳1 でほぼ飽和」は、O∈[1,2) の飽和関数なら自然に説明できるが、生の Freq^θ なら θ 増加で頻度が指数的に支配するので飽和では説明できない。**論文自身の実測が実装式の側を支持している** |
| **2** | §4.3「与えられた容量内で」— ノード/エッジへの**容量配分は未記載** | `cap_node=40 / cap_edge=60`（占有量単位。実エントリ数は 20/20） | ★§5.2 の「探索により選定するのは w と θ のみ」と矛盾する**隠れパラメータ**。配分の根拠（実測のノード/エッジ比？）を書くか、配分感度を示して「効かない」ことを示す必要 |
| **3** | 「**全体の重み w**」と単一で記述 | `w_node` と `w_edge` の2つ。既定 `w_edge = 3·w_node`。図8の軸ラベルにのみ `w_edge=3·w_node` と記載 | ★本文に説明がない。3倍の根拠も未記載。§5.2 の記述と食い違う |
| **4** | `Priority = Base + w·Value`（size の除算なし） | `Base + w·Value/size` | 実害なし。**プールを分けたので pool 内で size は定数**（node=2, edge=3）→ w の定数倍に吸収される。実効値は w_node/2=50、w_edge/3=100（実効比は3倍ではなく**2倍**）。§4.3 の「占有量を考慮して」がこれに対応するとも読めるので注記レベル |

**記号衝突は無い**（Freq/Close/Deg/Base/Value/Priority と明確に命名されている）。v6 草稿にあった H の多重定義問題は解消済み。

### 1.4 ★図表間の設定不一致（本文とも矛盾）

| 図表 | 生成スクリプト | 次数の設定 | 結果 |
|---|---|---|---|
| 表1・図7 | `figs/plot_proposed_win.py`（`args_for` は `node_deg_exp` を渡さない → 既定 1.0） | **γ=1（次数 ON）** | VLDB 51.9 (+6.6), Amazon 51.4 (+7.1) |
| 図8（w スイープ） | `figs/plot_wsweep_dualpool.py` L36 `node_deg_exp=0.0  # degree除去` | **γ=0（次数 OFF）** | w≈100 で約52%、LRU +7.0。凡例も `PROPOSED dual (hop+O)` |
| 本文 §5.2 | — | 「β=γ=1 と固定」 | 図8 と矛盾 |

seed も違う（表1/図7 は `[1,7,13,99,123]` の5 seed、図8 は `[1,7,13]` の3 seed）。

> つまり **「次数を外した方が良い」という結果が既に図8に出ている**。これは目的2（性能向上がどの構造情報に由来するか）の答えの一部であり、対照実験で正面から測って本文と図を整合させるのが正しい処置。

## 2. 追加実験①：構造情報の要素別寄与（目的2 の本体）

### 2.1 5要素の定義（論文の記号で）

| 記号 | 要素 | ON | OFF | 実装フラグ | 状態 |
|---|---|---|---|---|---|
| **F** | Freq（使用回数） | θ=1 | θ=0 | `args.theta` | ✅ あり |
| **C** | Close（始点からの近さ） | `node_hop_exp=1` かつ `edge_use_hop=True` | `0` / `False` | 同左 | ✅ あり |
| **G** | Deg（次数、ノードのみ） | `node_deg_exp=1` | `0` | 同左 | ✅ あり |
| **B** | Base（LRU の最終アクセス時刻） | `Base=last_access` | `Base=0`（純スコア退去） | ⚠️ **要追加**（`_h_value` に `use_recency_base` フラグ、3行） | ❌ |
| **P** | プール分離（ノード/エッジ独立キャッシュ） | 別プール | 共有1プール | ⚠️ **要追加**（`run_dualpool` に共有モード、約10行） | ❌ |

* C は node/edge で2フラグに分かれているので、**1ビット因子にするため必ず同時に切り替える**。
* **P の OFF を `base.run_policy(..., "reuse_score")` で代用してはいけない。** そちらは `hop_prior` がエッジにも `Deg` を掛けるため、「プール共有」と「エッジが次数を使う」の2変化が同時に起きて交絡する。共有モードは *prior は種別ごと（エッジは hop のみ）に保ったまま、1つのキャッシュに入れる* 実装にする。
* B の OFF は「LRU 土台が本当に必要か」を測る。論文 §4.2 の「加法形式にしたのは既存方式の優先順位を維持したまま構造情報による補正のみを行うため」という主張の直接検証になる。

### 2.2 完全実施要因（2^5 = 32セル）とアンカー

| セル | 意味 | 期待値 |
|---|---|---|
| F=C=G=0, B=1, P=0 | **共有 LRU** | 表1 の LRU（VLDB 45.3 / Amazon 44.3）と**一致すべき** ← sanity check |
| F=C=G=0, B=1, P=1 | **分離 LRU** ← ★最重要の欠落対照 | 「容量を分けただけ」の寄与 |
| F=C=G=1, B=1, P=1 | 提案（完成版, γ=1） | 表1 の 51.9 / 51.4 |
| F=1,C=1,G=0, B=1,P=1 | 図8 の設定（hop+O） | 約52%（+7.0） |
| B=0 の各セル | 純スコア退去 | LRU 土台の必要性 |
| 全部 OFF | Value≡1, Base=0 | 実質 FIFO/任意順（下限の参照点） |

**評価指標**：主効果 = mean(hit | 因子ON) − mean(hit | 因子OFF)（他4因子の全16組合せで平均するので交絡が消える）。併せて単独ON（その因子だけ）・leave-one-out（その因子だけ OFF ＝限界寄与）・2因子交互作用。**ノード別／エッジ別／全体の3系列で出す**（論文図7と同じ切り口。エッジで G が負に効くことが数値で出る）。

### 2.3 なぜこの設計が論文図として強いか

* `w=0` で Value が消えるので、**表の一角が既存手法そのもの**になり、主効果が「LRU から何 pt 積めたか」の分解として読める。
* **分離 LRU セルが入ることで、+6.6 pt の内訳が「プール分離 x pt ＋ スコア y pt」に分解できる**。査読で最初に来る「その改善はスコアのおかげか、それとも容量分割のおかげか」に先回りできる。
* G の主効果がノードで正・エッジで負（またはノードでもほぼ0）と出れば、§3 の分析（次数の働きがノードとエッジで逆）が**置換方針の性能として**裏づけられ、同時に §1.4 の図8/本文の不整合も自然に解消される（「γ=0 を採用する」と書ける）。

### 2.4 条件設計と反復

| 条件 | セル数 | 内容 |
|---|---|---|
| **主条件** α=0.1, RW 1,000本, 容量100, {VLDB, Amazon} | 2 × 32 = 64 | 完全実施要因。主効果＋2因子交互作用 |
| **副条件** α=0.05 / 0.02（regime 境界）、同上 | 4 × 12 = 48 | 12セル＝全OFF＋単独ON×5＋LOO×5＋全ON。主効果は出せないが単独寄与と限界寄与の2通りで順位が示せる |
| **反復** | 各セル seed 5点（`[1,7,13,99,123]`） | 主効果に標準誤差／信頼区間。**ノイズ床を図に水平線で明示**する |

* 実行は**仮想サーバシミュレータのみで足りる**（ヒット率はアクセス列 × 割当 × 方策の純関数）。実分散は不要。
* 64＋48セル × 5 seed ≒ 560 ラン。1ラン数十秒なら数時間オーダ。**まず主条件64セル×3 seed で当たりを取る**のが安全。

### 2.5 出力する図表

1. **主効果棒グラフ**（グラフ×{node, edge, overall} のパネル）。誤差棒＋ノイズ床線。← 本命
2. **階段図**：共有LRU → +分離 → +Close → +Freq → +Deg の増分。目的2 の答えを1枚で示す。
3. 32セル表（付録）／2因子交互作用行列（C×G が打消しなら「構造は冗長」の証拠）。

## 3. 追加実験②：パラメータの決め方

### 3.1 現状（§5.2）— ここは既に良く整理されている

| 層 | パラメータ | 決め方 | 論文の記載 |
|---|---|---|---|
| 自動（実行中） | μ_hop, s_hop, μ_deg, s_deg | Welford で逐次更新 | ✅「実行中に自動で定まるため、グラフごとの手動調整を要さない」 |
| 設計として固定 | β = γ = 1 | 「近さと次数を同程度に扱うため」 | ✅ 記載あり（ただし §1.4 の通り図8 は γ=0） |
| 探索で決定 | θ, w | 仮想サーバ上の探索。w は山なりの最大（w≈100）、θ≳1 で飽和 | ✅ 記載あり |
| **未記載（隠れ）** | **C_F=5、容量配分 40/60、w_edge/w_node=3** | 既定値のまま | ❌ **記載なし** |

### 3.2 やるべきこと（優先順）

1. **隠れパラメータ3つの開示＋感度**（最優先・安い）
   * C_F ∈ {1, 2, 5, 10, 20}、容量配分 ∈ {20/80, 30/70, 40/60, 50/50, 60/40}、w_edge/w_node ∈ {1, 2, 3, 5} の 1D スイープ。
   * **狙いは「効かないことを示す」こと。** 平坦なら「既定値で良い、探索対象は w と θ のみ」という §5.2 の主張がそのまま通る。効くなら決め方の規則（例：配分は実測のノード/エッジアクセス比）を書く。
2. **最適 w のグラフ間一致**（安い・効果大）
   * 図8 は VLDB のみ。**Amazon を重ねる**。ピークが両グラフとも w≈容量 にあれば「**w ≈ 容量**という規則で決まる」＝グラフ非依存の決定則を主張できる。容量も変えて w*∝cap を確認できればさらに強い。
3. **山なりの平坦性を定量化**（安い）
   * 「w ∈ [50, 200] なら最良から −0.5 pt 以内」のように許容幅を数値で書く。**実用上チューニング不要**という主張になり、「データセット依存」という弱点を打ち消す。`figs/plot_wsweep_dualpool.py` に LRU 水準線と許容帯を追加するだけ。
4. **θ は固定できることを示す**（ほぼ済み）
   * §5.4 の「θ=0 で 48.4%、θ≳1 で飽和」に θ=0.5/1/2/3 を足して飽和曲線として描けば、**θ=1 固定を正当化**でき、探索対象は w だけに縮む。
5. **汎化の実証（train/test 分割）**
   * 現在 `plot_proposed_win.py` は seed 5点平均だが、**w を選んだ seed と評価 seed が同じ**。始点・seed を tuning 用と held-out 用に分け、held-out で改善が残ることを示す。dualpool 系列では過去に「tuning seed 42 を検証から除外」という運用をした実績があるので、同じ規律を戻すだけ。

### 3.3 「データセット依存か」への答え方（推奨する言い方）

> 正規化定数（μ, s）はデータから自動決定されるため**グラフ依存の手動調整は不要**。設計値 β, γ は構造分析から固定。探索対象は w のみで、**その最適値は容量に比例する（w ≈ C）という規則で近似でき、両グラフで一致する**。さらに最適点近傍は平坦であり、w を規則値から ±2 倍ずらしても劣化は X pt 以内である。

この形にできれば、「パラメータがデータセット依存」は弱点ではなく**設計として説明済み**になる。§7（今後の展望）に挙げている「w や θ の自動決定」も、2 の結果があれば部分的に達成済みと書ける。

## 6. 参考：`paper_draft_v6.md`（別系列）との差分

v6 草稿は `reuse_score` 系列で、IN 稿とは別物。主な違い：

| 項目 | IN 稿（本計画の対象） | v6 草稿 |
|---|---|---|
| 土台 | `Base + w·Value`（LRU、w=0 で厳密 LRU） | Algorithm 1 は「スコア最小を退去」＝純スコア退去 |
| 構造項 | z標準化＋logistic、[1,2) | `(1−α)^(β·hop)·deg^γ`（絶対式） |
| 学習項 | なし | `Learn = 1 + λ·lw`（二段階運用） |
| プール | ノード/エッジ独立 | 共有 |
| 評価 | ヒット率（α=0.1, RW1000, cap100） | ヒット率＋RTT 実行時間（最大160秒削減） |
| 記号 | Freq/Close/Deg/Base/Value/Priority | H が「アクセス回数」「距離項」「退去優先度」で三重衝突 |

v6 側の実装は `split_remote_server_reuse_score.py`（`combine="reuse_score"`）で、そちらは**論文式と実装が骨格レベルで不一致**（純スコア退去 vs LRU土台、絶対式 vs 標準化、A/B/C 重みが argmin に効かない等）。v6 を別途仕上げる場合は、その論文側を実装に合わせて改稿する必要がある。**IN 稿にはこの問題はない。**

## 7. 実装の実体と設計上の論点（コードリーディング結果）

### 7.1 1アクセスの処理順序（`virtual_server_dualpool.authorize_dual`）

```
候補 target が来る（_select_next が近傍をシャッフルし、認可が通った最初の1件を採用）
  ├ is_edge 判定 → edge_cache / node_cache を選択、prior_fn = edge_prior / node_prior
  ├ ckey = (start_node, entity_key)
  ├ ヒット時: hit++ → bump_prior(ckey, prior) → cache[ckey]
  │            └ __getitem__: freq += 1; clock += 1; last_access = clock;
  │                           H[ckey] = last_access + w·V/size   ← Priority 再計算
  └ ミス時: miss++ → owner 解決 → is_locally_allowed（deny リスト照合）
             → bump_prior(ckey, prior)            ← 挿入前に構造 prior を記録
             → cache[ckey] = allowed
                └ __setitem__: clock += 1; last_access = clock; freq = 1;
                               H[ckey] = last_access + w·V/size; _evict_until_fit()
```

* `Priority` は **エントリごとの静的スナップショット**（最終アクセス時に計算して保存）。触られていないエントリの値は動かない。LRU のタイムスタンプと同じ性質で、ρ=0 の限りこれは正しい（ρ>0 だけは `_effective_h` で動的評価している）。
* `bump_prior` は **max 保持**（`prior > cur` なら更新）＝「これまでに観測した最小 hop」を近似。ただし μ,s が時間で動くため、異なる時点で計算した prior 同士の比較は厳密な最小 hop 追跡にならない（軽微）。
* `freq` と `prior_val` は退去時に破棄される（`_evict_until_fit`）→ Freq は論文どおり「保持されている間の使用回数」。
* 退去は `min(self.H, key=...)` の**線形走査**。現在は 1プール 20 エントリなので無害だが、実容量（グラフの10%等）へスケールさせるなら遅延削除付きヒープが必要。

### 7.2 実効パラメータ（既定値と、`/size` 吸収後の実効値）

| | 論文表記 | 実装既定 | 実効値 |
|---|---|---|---|
| 容量 | 100 | `cap_node=40`, `cap_edge=60`（占有量単位） | ノード 20 エントリ / エッジ 20 エントリ（size = 2 / 3） |
| 重み | w ≃ 100 | `w_node=100`, `w_edge=300` | `w/size` → ノード 50、エッジ 100 |
| Value の値域 | — | node: O·Close·Deg ∈ [1,8)、edge: O·Close ∈ [1,4) | ボーナス幅 = ノード 3.5·w_n = **350**、エッジ 1.0·w_e = **300** |

> **`w_edge = 3·w_node` は導出できる。** ボーナス幅を両プールで等しくする条件は 3.5·w_n = 1.0·w_e、すなわち **w_e = 3.5·w_n**。実装の 3 倍はこれのほぼ最適値であり、恣意的な定数ではない。論文には「エッジは因子が1つ少なく（Deg なし）占有量が 1.5 倍なので、構造ボーナスの値域を揃えるため w_edge = 3·w_node とした」と**書ける**。

### 7.3 ★最優先で直すべき2点

**(1) seed が独立していない。**
`run_policy` / `run_dualpool` はともに `rng = random.Random(args.seed + i)`（i = walk 番号）。
seeds = `[1,7,13,99,123]`、walks = 1000 のとき RNG ストリーム集合は {1..1000}, {7..1006}, … となり、**seed 1 と 7 は 1000 本中 994 本が同一のウォーク**。つまり「5 seed の平均 ± sd」は独立反復ではなく、ウォーク集合を数本ずらしただけの測定であり、**誤差棒は真のばらつきを大幅に過小評価**し、「held-out seed で検証」も成立していない。
→ 修正は 1 行：`rng = random.Random(args.seed * 1_000_003 + i)`。修正後に誤差棒を取り直す必要がある。

**(2) ARC を計算しているのに図表から外している。**
`figs/plot_proposed_win.py` は `methods = ["LRU","ARC","PROPOSED","memo"]` で ARC も回しているが、`--no-arc` オプションがあり、生成物も `proposed_win_*_noarc.png` 系列。論文の表1・図7 は ARC なし（LRU と提案のみ）。ARC は LRU より強いベースラインなので、**対 ARC の優位幅が示されないままでは「+6.6/+7.1 pt」の解釈が過大に見える**。表1 に ARC 行を追加するのが最優先。

### 7.4 設計として再考の価値がある点

| 論点 | 現状 | 問題 | 代替案 |
|---|---|---|---|
| **正規化が半端** | Close と Deg は z標準化＋logistic で [1,2)。**Freq は飽和関数（C_F=5）で [1,2)、Base は生の論理時刻** | 論文は「尺度が異なるので標準化する」と書いているのに、5要素のうち2つだけを標準化している。Freq に C_F という未記載の定数が残り、Base は無界 | **Freq も Recency も同じ z標準化＋logistic に統一**：`Recency = 1+σ((μ_age−age)/s_age)`、`Freq̂ = 1+σ((freq−μ_f)/s_f)` として `Priority = Recency^δ·Freq̂^θ·Close^β·Deg^γ` の完全乗法形にする。C_F が消え、w が δ（有界な指数）に置き換わり、全パラメータが同じ意味になる |
| **w が尺度依存** | `Priority = last_access + w·V/size`。last_access は論理クロックで無界 | w の最適値は「在駐エントリの last_access のばらつき」に依存する。ばらつきは容量とアクセス率で決まるため、**w は (容量, walks, α) ごとに再調整が必要**。これが「w を探索で決める」しかない理由 | (a) last_access を**在駐エントリ内の順位**に置き換えると w が無次元になり条件間で転移する。(b) より簡単に、**w を実行中に自動決定**：`w* ≈ IQR(last_access of residents) / range(V/size)`。ばらつき ∝ 容量 なので **w ∝ 容量**（実測の w≈100 @ cap=100 と整合）。§7 の「w の自動決定」がこれで達成できる |
| **容量配分 40/60** | 固定。ノード20/エッジ20 エントリ | 未記載の隠れパラメータ。アクセス比に対して最適か未検証 | 20/80〜60/40 をスイープ。平坦なら「等エントリ数で十分」と書ける。動的配分（ARC のように境界を自己調整）も選択肢 |
| **Welford 状態がプール間で共有** | `server.reuse_norm["hop"]` をノードとエッジで共用 | 二部グラフでは node の hop は偶数・edge は奇数に偏るため、μ_hop が両者の混合になる（差は約0.5 hop で軽微） | プールごとに独立の Welford 状態を持たせる（数行）。効果は小さいので優先度低 |
| **土台が LRU 固定** | Base = last_access | 論文の Base(e) は「既存キャッシュ方式の優先度」と一般化されているので、**式を変えずに ARC 土台に差し替えられる**。実装にも `StructuralARC` が既にある | ARC 土台版を表1 に併記。過去の実測（要再確認）では ARC 土台の方が強かった |
