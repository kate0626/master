### 読み取れること

1. **次数（Deg）は寄与しない。** overall で VLDB −0.48、Amazon −0.03。エッジは定義上 Deg を使わないので Δ は厳密に 0.00、ノードでも VLDB は −1.01 で**外した方が良い**。
   → 論文 §5.2 の「β=γ=1 と固定」は **γ=0（次数は用いない）** に改めるべき。図8 が `node_deg_exp=0.0` で描かれていたことと整合する（本文と図の不一致が解消する）。

2. **構造スコア（Close）と履歴（Freq）はエッジで効く。** edge で +5.5〜5.6（VLDB）/ +3.2〜3.9（Amazon）、node ではどちらも +1.0 前後。
   → エッジプールは `Value = Freq^θ · Close^β` の2因子しか持たないが、**スコアによる改善はほぼエッジ側で生まれている**。

3. **Base（LRU の最終アクセス時刻）が最大。** node で +13.2/+7.9、overall で +7.4/+4.2。
   → 論文 §4.2 の「加法形式にしたのは既存方式の優先順位を維持したまま構造情報による補正のみを行うため」という設計判断が、数値で裏づけられた（純スコア退去にすると overall が 4〜7 pt 落ちる）。

4. **プール分離は全体ヒット率をほぼ変えず、ノード/エッジの配分を変える。** Pool の Δ は overall で −0.08 / +0.16（実質ゼロ）だが、内訳は **node −5.0/−2.6、edge +4.32/+2.64**。
   共有プールにするとスコアがノードに味方して **edge が餓死する**（VLDB: node 67.81 / edge 38.64）。分離するとバランスする（node 62.84 / edge 42.96）。
   → 論文では「プール分離は全体ヒット率の向上ではなく、**エッジのヒット率を +2.6〜4.3 pt 改善して型間の偏りを是正する**機構」と書くのが正確。エッジも独立した認可対象である本設定では、片方の型が極端に低いヒット率になるのを避ける意味がある。

## 4. その他、論文の記載で直すべき点

1. **表3 の VLDB のグラフ規模が実験と合わない。** 論文は VLDB を 2,856,664ノード / 13,511,731エッジ と記載しているが、表1 の数値を再現したファイル `dataset/Louvain/graph/vldb.gr` は **317,080ノード / 1,049,866エッジ**。Amazon0601 は 403,394 / 3,387,388 で記載どおり一致する。VLDB の規模は出典[13]の値を転記したものと思われるので、**実験に使った実際の規模に直す**か、前処理（サンプリング等）を明記する必要がある。
2. **ヒット率は「越境のみ」ではなく全認可に対する値。** 実測でミス時の認可のうち越境は VLDB 51.2% / Amazon 49.9%。パーティションは型を無視したモジュロ分割（node は `n%2`、edge は `(u+v)%2`）で、両サーバがノードもエッジも所有している。§5.1 に配置方法を明記すべき。

4. **未記載パラメータ**：C_F=5、容量配分 node40/edge60、`w_edge = 3·w_node`。うち w の比は「エッジは因子が1つ少なく占有量が1.5倍なので構造ボーナスの値域を揃えるため」と**導出として書ける**（3.5倍が値域等化の理論値）。

### deny が効かない理由（要修正）

deny テーブル（`base/auth-many-server/data/splits/<graph>/0.3/node_to_starts_server{0,1}.json`）に登場する始点は **{1, 2, 3, 4, 10} のみ**で、**start=0 を拒否しているエンティティは 0 件（0.0%）**。図の生成スクリプトはすべて `--start-nodes 0` が既定なので、deny を読み込んでも一件も適用されない。実測でも 1 hop あたりの認可回数がちょうど 1.000（deny 30% なら棄却分だけ ≈1.43 になる）。

さらに、図の生成は `VirtualCluster(edges, 2, None)` なので **deny テーブルを読み込んでもいない**（`partition_dir=None` → deny 空、パーティションもモジュロ）。したがって表1・図7・図8 は **「deny なし・モジュロ分割・始点0」** の条件。

始点を deny が効く 1 に変えると（E→F）全手法が底上げされるが（LRU 28.59→31.08、memo 58.60→64.80）、**順位は変わらない**（−1.13 → −1.32）。**deny の有無は結論に影響しない。**

### 実分割は事実上「ノードサーバ／エッジサーバ」

```
実分割:  srv0: node=290,155  edge= 83,789
         srv1: node= 26,925  edge=966,077
モジュロ: srv0: node=158,472  edge=498,845
         srv1: node=158,608  edge=551,021
```

実分割ではノードとエッジがほぼ型で分かれる。要求側は「現在のエンティティを所有するサーバ」なので、srv0（ノード持ち）はエッジばかりを要求し、srv1 はノードばかりを要求する。すると**各サーバで 40/60 に分けた片方が遊ぶ**ため容量が実質半分になる。実測の Pool の Δ = **−5.77**（共有プールにすると 58.03 まで上がる）はこれで説明できる。越境率も 51.2% → 85.8%。

> つまり **プール分離の有効性はパーティションのしかたに完全に依存する**。型混在（モジュロ）なら +4 pt、型分離（実分割）なら −5.8 pt。論文§4.3 のプール分離を主張するなら、配置方法を明記し、型混在配置を前提として書く必要がある。

| β | 1.49 pt | 1.33 pt | 0.5 / 0.5 | +0.29 / +0.19 |
| C_F | 0.62 pt | 1.03 pt | 10 / 10 | +0.02 / +0.03 |

## 2. 結論（論文にそのまま書ける3点）

1. **動作点はほぼ最適。** 7軸すべてで最良値との差が +0.00〜+0.56 pt。w=100 は両グラフで厳密に最良、cap_node=40 は VLDB で厳密に最良。→「パラメータを都合よく選んだから勝った」への直接の反証。
2. **平坦性が高く、LRU 超えは単一設定に依存しない。** w は **25〜800（32倍の幅）で LRU を上回り続ける**（Amazon +4.03〜+7.21、VLDB +1.62〜+6.90）。cap_node は 30〜70 で上回る。θ / β / γ / C_F / w_ratio は掃引範囲の全域で上回る。
3. **結果を左右するのは「容量配分」と「w」の2軸だけ**（7〜10 pt）。残り5軸は 0.6〜4.2 pt。
   - 論文§5.2 は「探索するのは θ と w のみ」と書いているが、**実測では容量配分が最大の効き幅**。未記載のままだと隠れた調整に見えるので、開示して 30〜70 の平坦域を示すべき。
   - **C_F は 0.6〜1.0 pt しか効かない** → 「既定値で十分・探索不要」と書ける根拠。
4. **γ の最良は両グラフで 0.5、動作点の γ=1 は既に劣化側**（VLDB は γ=2 で 52.95→48.73 と急落、効き幅 4.23 pt）。β も最良 0.5。LOO の「次数は不要」と整合。

## 3. 再調整では ARC を超えられない（負の結果）

各軸の最良値を組み合わせた構成を、始点を振って検証した。

| | VLDB 平均 vs LRU | vs ARC | ARC超え | Amazon 平均 vs LRU | vs ARC | ARC超え |
|---|---|---|---|---|---|---|
| 動作点（論文） | +3.20 | **−0.05** | 2/5 | +2.56 | **−0.67** | 1/10 |
| 調整版A（θ1.5, β0.5, **γ0.5**, cap50/50, C_F10, ratio5） | +3.18 | **−0.07** | 1/5 | +2.91 | **−0.32** | 4/10 |
| 調整版B（同上で **γ=0**） | +2.99 | **−0.26** | 1/5 | +2.70 | **−0.54** | 2/10 |

- 単一始点(0)の OAT で見えた +0.1〜0.3 pt の改善余地は、**始点を振ると消える**（＝OAT の最良値は始点0への過適合）。
- **パラメータ調整で ARC を安定して超えることはできない。** ARC 超えを狙うなら機構を変える（ARC 土台の `StructuralARC` / `run_dualpool_arc`）か、主張を「ARC と同等」に改める必要がある。
- 副産物として、**動作点は始点平均でも再調整版とほぼ同じ**（VLDB 53.37 vs 53.35 / 53.15、Amazon 36.40 vs 36.75 / 36.53）。パラメータ選定の妥当性はむしろ強化された。

# 追記3：足し合わせが成立する分解（Shapley）と Pool の値の訂正（2026-08-29）

**駆動** `run_shapley_decomposition.py` / **作図** `figs/plot_shapley_decomposition.py` / **図** `figs/shapley_decomposition.png` / **データ** `results/shapley_{VLDB,Amazon}{,_raw}.csv`
条件は表1 と同じ（α=0.1、RW1000、cap100、始点0、モジュロ分割・deny なし、seed 1/7/13/99/123）。

## 1. leave-one-out の値は足し合わせても総改善にならない

LOO の Δ_i = v(全部) − v(全部から i を外す) は**限界寄与**であり、要素間に交互作用があると
Σ Δ_i ≠ v(全部) − v(なし) になる。実測：

| | Σ LOO | 総改善 | 差（交互作用） |
|---|---|---|---|
| VLDB | +6.32 | **+6.56** | −0.24 |
| Amazon | +4.71 | **+7.05** | −2.34 |

（Base を含めると Σ LOO は VLDB +13.7 / Amazon +9.1 になりさらに乖離する。Base は LRU 側に
もともと入っている要素なので「LRU に何を足したか」の分解には含めない。）

## 2. Shapley 値なら厳密に足し合わせられる

φ_i = Σ_{S⊆N\{i}} |S|!(n−|S|−1)!/n! · [v(S∪{i}) − v(S)]、性質 Σφ_i = v(N) − v(∅)。
2^4 = 16 セルすべてを seed 別に測って計算した。**v(∅) は実測 LRU と厳密一致（残差 +0.00）**。

| 要素 | VLDB Shapley | Amazon Shapley | （参考）LOO VLDB / Amazon | （参考）単独ON |
|---|---|---|---|---|
| **Close**（始点からの近さ） | **+3.38±0.04** | **+2.85±0.03** | +3.33 / +1.99 | +3.17 / +2.82 |
| **Freq**（使用回数） | **+2.89±0.01** | **+3.08±0.03** | +3.44 / +2.50 | +2.26 / +2.68 |
| **Deg**（ノード次数） | +0.17±0.03 | +0.58±0.06 | **−0.53 / −0.12** | +0.68 / +0.91 |
| **Pool**（プール分離） | +0.12±0.08 | +0.54±0.04 | +0.09 / +0.34 | +0.10 / −0.00 |
| **合計** | **+6.56** | **+7.05** | +6.32 / +4.71 | +6.22 / +6.41 |
| 総改善（提案−LRU） | **+6.56** | **+7.05** | — | — |

**改善のほぼ全部が Freq と Close の2要素**（VLDB 6.27/6.56 = 96%、Amazon 5.93/7.05 = 84%）。

**Deg は「代替財」**：単独では効く（+0.68/+0.91）が、Freq と Close が入っていると冗長で
むしろ邪魔（LOO が負）。Shapley はその平均を取るので小さな正になる。
→ 論文では「次数は他の信号が弱いときだけ効く補助的な特徴」と書けば全指標が整合する。

## 3. ★ Pool の値の訂正（追記1 の +4.4 は誤り）

追記1 で「Pool の LOO = +4.45/+4.46」と報告したが、これは**共有プール側の実装の副作用**だった。

- `_h_value` は `Priority = last_access + w·V/size` で、占有量は node=2 / edge=3。
- 共有プールで w を型別（w_node=100 / w_edge=300）に保つと、スコアが全 OFF（V=1）でも
  node は +50、edge は +100 の定数差が付き、**エッジ優先のバイアス**が残る。
  実測でこの構成の v(∅) は LRU より **−2.33（VLDB）/ −3.14（Amazon）pt 低かった**。
- 修正：共有プールでは単一 w（=w_node）を使い、prior に占有量を掛けて `/size` を打ち消す。
  これで V=1 のとき全キーの加点が同一定数 → **厳密に共有 LRU と同順**になる。

修正後の Pool の寄与は **+0.12 / +0.54 pt（Shapley）、+0.09 / +0.34 pt（LOO）**。
すなわち **プール分離は性能にほとんど寄与していない**。

> 論文への影響：§4.3 の「ノードとエッジを独立したキャッシュで管理する」は、
> 性能上の根拠が弱い。改善は Freq と Close で説明できる。プール分離を残すなら
> 「型ごとに異なる特徴（エッジは次数を使わない）を自然に扱える設計上の利点」
> として書き、性能寄与としては主張しないのが正確。
> なお追記1 の他の行（Freq / Close / Deg / Base）は共有プールを経由しないので影響なし。
